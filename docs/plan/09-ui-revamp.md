# 09 · `/mail` 工作台 UI 改版方案

> **状态：P0–P6 已全部实施（2026-08-21）。**实施中与本方案的偏离记在 §8。

参照物两个，性质不同，要分开对待：

- **`email.png`（小苹果 Pro 邮箱助手 v1.4.7）** —— 提供**布局与信息架构**。这是我们要对齐的目标形态。
- **`https://www.appleemail.top/mail.html`（v1.0.8）** —— 提供**视觉语言**。它是单文件 HTML（213 KB，
  一个内联 `<style>` 共 110 KB），布局是简单的「导航 + 表格」，比截图落后好几代，
  但配色、圆角、阴影、过渡这套 design language 与截图同源，可以直接量取。

下面第 1、2 节是对参照物的拆解（**结论都来自实测，不是印象**），第 3 节起是我们的改造方案。

## 1. 布局解剖（来自 `email.png`）

### 1.1 整体是「应用外壳」，不是文档流页面

这是与我们当前实现**最本质**的差异。参照物是一个撑满视口、自身不滚动的五段纵向结构：

```
┌────────────────────────────────────────────────────────────────┐
│ ① Header      logo+品牌 | 全局搜索(超宽) | 通知/AI/设置/帮助/头像 │ ~56px
├────────────────────────────────────────────────────────────────┤
│ ② Toolbar     添加邮箱 文件导入 导出全部 邮件规则 新建 群发 删除  │ ~52px
├───────────┬──────────────────┬─────────────────────────────────┤
│           │                  │ ④a 文件夹 Tabs + 筛选条          │
│ ③ 左栏    │ ④ 中栏           │    邮件列表                      │
│  CTA卡片  │  账号列表(表格)   ├─────────────────────────────────┤ ← 可拖拽
│  分组面板 │  快速筛选/分页    │ ④b 详情操作条(回复/转发/删除…)   │
│           │                  │    邮件详情                      │
├───────────┴──────────────────┴─────────────────────────────────┤
│ ⑤ StatusBar  0账号 ●在线0 ●错误0 ●空闲0 ✉未读0 收件箱 | v1.4.7 时钟│ ~30px
└────────────────────────────────────────────────────────────────┘
```

**没有传统 Footer。**底部是一条常驻状态栏。

### 1.2 栏宽与高度

按截图像素占比换算（原图 2460×1268，等效视口约 1230×900 CSS px；数值取整后是设计意图，不必逐像素复刻）：

| 区域 | 占比 | 建议值 |
|---|---|---|
| 左栏 | 19% | `280–320px` 固定，可折叠 |
| 中栏 | 39% | `flex: 1 1 auto`，`min-width: 420px` |
| 右栏 | 42% | `flex: 1 1 auto`，`min-width: 480px` |
| Header / Toolbar / StatusBar | — | `56 / 52 / 30 px` |
| 右栏内部 邮件列表 : 详情 | ≈ 55 : 45 | 默认 `1:1`，拖拽分隔线可调 |

### 1.3 各区域的关键设计决策

**① Header** —— 品牌区是「渐变图标块（带 PRO 角标）+ 主标题 + 橙色副品牌词 + 灰色一行 slogan」两行结构；
中间是**贯穿式全局搜索**（pill 形、浅灰填充、占据近半宽度），placeholder 写明可搜三类对象
（邮箱账号 / 邮件主题 / 发件人）——这是把「搜账号」和「搜邮件」合并成一个入口的强信号；
右侧五个等距图标按钮，通知带红点角标，末位是圆形头像。

**② Toolbar** —— 全局动作条，pill 按钮（图标 + 文字）。语义分层清晰：
主操作「添加邮箱」用品牌色描边 + 浅色底，中间五个是中性白底细描边，「删除」用红字红边。
按钮之间用间距而非分隔线分组。

**③ 左栏** —— 三层结构：
1. 顶部一张**大 CTA 卡片**「开始收件」（浅蓝渐变底、圆角 16px、居中图标+文字），把最高频动作从菜单里提出来；
2. 「邮箱分组」面板标题行，右侧挂 `+`（新建分组）和折叠全部两个图标按钮；
3. **状态维度的二级树** —— 一级是集合（所有分组 / 回收站 / 辅助邮箱），
   二级固定是四个登录状态（尚未登录 / 登录成功 / 登录失败 / 存在未读），
   每行「彩色圆点 + 标签 + 右侧计数」，选中行浅蓝底圆角高亮。

   这不是普通分组树，而是**「分组 × 状态」交叉筛选面板**。语义比我们现在的 `GroupTree` 多一个维度。

**④ 中栏** —— 标题行「账号列表 + `0 个账号` 徽章 + 右侧图标组（移动/刷新/排序）」，
下面是独立的「快速筛选当前列表」输入框（与 Header 全局搜索职责分离：这个只过滤已加载的列表），
再下面是**带表头的表格**（复选框 / # / 邮箱账号 / 分组 / 邮件），底部左「空」状态字 + 右分页 `1/1`。

**⑤ 右栏** —— 上下两段：
- 上段：文件夹 Tabs（收件箱/发件箱/草稿箱/归档/已删除，**下划线式**、选中项蓝字蓝下划线）→
  工具行（全选复选框、归档、删除、标记图标 ‖ **分段 pill 筛选**：全部/未读/已读/加星 ‖ 右侧分页与折叠）→ 列表/空状态。
- 下段：详情操作条（回复/转发 ‖ 删除/标为未读/复制 ‖ 右侧全屏、折叠）→ 详情/空状态。

两段各有自己的空状态插画（灰色信封图标 + 一句说明），**空状态是被认真设计过的**，不是一行灰字。

**⑥ StatusBar** —— 左侧一排带彩色圆点的实时计数（账号总数 / 在线 / 错误 / 空闲 / 未读 / 当前文件夹邮件数 / 未接收），
用细竖线分隔；右侧版本号 + 实时时钟。

## 2. 视觉语言（来自 `mail.html` 实测）

`grep` 统计 CSS 中的色值频次，得到的调色板：

| 角色 | 值 | 出现次数 |
|---|---|---|
| **品牌主色** | `#667eea` → `#764ba2` 线性渐变 135° | 62 / 14 |
| 危险 | `#f5576c` | 10 |
| 成功 | `#059669` | 6 |
| 警告 | `#d97706` | 5 |
| 紫（次强调） | `#8b5cf6` / `#7c3aed` | 5 |
| 中性文本 | `#1e293b`（主） `#475569` `#64748b`（次） `#9ca3af`（弱） | slate 全家桶 |
| 线 / 填充 | `#e2e8f0` `#e5e7eb` / `#f1f5f9` | — |

其余可复用的规律：

- **圆角**：`50px`（pill：nav-tab、按钮）/ `12px`（图标块）/ `16px`（卡片）
- **阴影极浅**：`0 1px 12px rgba(0,0,0,.06)`、`0 4px 20px rgba(0,0,0,.06)`
- **过渡统一**：`all .3s cubic-bezier(.4,0,.2,1)`；hover 常配 `translateY(-1px) scale(1.03)`
- **品牌文字**：`background: linear-gradient(...)` + `background-clip: text` + 透明文字色
- 字体栈 `-apple-system, BlinkMacSystemFont, "Segoe UI", …`，`line-height: 1.6`
- 图标用 Font Awesome 6（CDN）

### 2.1 三个**不要**照抄的点

| 参照物做法 | 为什么不抄 | 我们怎么做 |
|---|---|---|
| `html { zoom: 0.9 }` 全局缩放 | 破坏 Tailwind 断点计算，且压掉用户自己的浏览器缩放，可访问性倒退 | 密度用 Kumo `size="sm"` + 自定义行高令牌控制 |
| `rgba(255,255,255,.95)` + `backdrop-filter` 玻璃顶栏 | 写死白色，暗色模式直接崩 | 用 `--color-kumo-base` + 阴影分层；毛玻璃如果要，值走 `light-dark()` |
| Font Awesome CDN | 项目已有 `@phosphor-icons/react`，再引一套图标是净负担，且 CDN 是外部依赖 | 全部映射到 Phosphor |

## 4. 关键决策：怎样在 Kumo 约束下做这套视觉

`AGENTS.md §6.2` 与 ESLint 规则明令：颜色一律走 Kumo 语义令牌，禁止原始 Tailwind 色类和 `dark:` 前缀。
参照物那套写死的 hex 与之直接冲突。**解法是改令牌，不是绕过令牌**。

Kumo 的令牌是 `@theme` 里的 CSS 变量（`node_modules/@cloudflare/kumo/dist/styles/theme-kumo.css`，
形如 `--color-kumo-brand: light-dark(…)`）。在 `src/style.css` 里追加一个 `@theme` 块覆盖即可：

```css
/* style.css —— 排在 @import "tailwindcss" 之后 */
@theme {
  /* 品牌色：Cloudflare 橙 → 参照物紫蓝。值仍走 light-dark()，暗色自动成立。 */
  --color-kumo-brand:       light-dark(#667eea, #8b9dff);
  --color-kumo-brand-hover: light-dark(#5a6fd8, #a0aeff);
  --text-color-kumo-brand:  light-dark(#667eea, #8b9dff);
  --color-kumo-focus:       light-dark(#667eea, #8b9dff);
}
```

这样做的好处：组件代码里**继续只写 `bg-kumo-brand` 这类语义类**，ESLint 不用开口子，暗色模式免费得到。

Kumo 确实没有的东西，另起一套 `--ebx-*` 自有令牌，同样强制 `light-dark()`：

```css
@theme {
  /* 品牌渐变（Kumo 没有渐变令牌） */
  --ebx-gradient-brand: linear-gradient(135deg, #667eea 0%, #764ba2 100%);

  /* 账号状态圆点：与「登录成功/失败/未登录/存在未读」四态一一对应 */
  --ebx-dot-online: light-dark(#059669, #34d399);
  --ebx-dot-error:  light-dark(#f5576c, #fb7185);
  --ebx-dot-idle:   light-dark(#9ca3af, #6b7280);
  --ebx-dot-unread: light-dark(#667eea, #8b9dff);

  /* 外壳尺寸，供布局与 JS 拖拽共用一个真源 */
  --ebx-header-h: 56px;
  --ebx-toolbar-h: 52px;
  --ebx-status-h: 30px;
  --ebx-sidebar-w: 300px;
}
```

> ESLint 那条颜色规则要确认是否会误伤 `--ebx-*`。如果它按类名前缀匹配，`bg-[var(--ebx-dot-online)]`
> 这类写法可能被拦——那就把圆点做成组件（`<StatusDot tone="online" />`），
> 颜色收在组件内部一处，反而更好维护。

## 7. 风险与坑

1. **iframe 吞鼠标事件** —— 详情正文是 `sandbox` iframe。`SplitPane` 拖拽时指针一旦进入 iframe，
   `mousemove` 就断了，表现为「拖到一半卡住」。拖拽期间必须给 iframe 挂 `pointer-events: none`。
2. **flex 链路里的虚拟列表** —— `VirtualList` 的祖先容器每一层都要 `min-h-0`，
   否则内容会把 flex 容器撑破，滚动条跑到外壳上，整个固定布局失效。这是改外壳时最容易踩的一个。
3. **`min-h-[calc(100vh-113px)]` 必须删干净** —— 这类魔法数一旦和新外壳共存，会出现双滚动条。
4. **`100vh` 在移动端 Safari 会被地址栏吃掉** —— 统一用 `100dvh`。
5. **响应式不能丢** —— 参照物是纯桌面产品（`zoom:.9` 就是明证），我们必须保住
   `AGENTS.md §6.6` 的三档：≥1280 三栏并列 / 768–1280 左栏折进 `Select` / <768 单栏层级导航。
   移动端下 `SplitPane` 退化为「列表 ↔ 详情」层级切换，不做拖拽。
6. **`GroupTree` 的 `onSelect` 签名要变** —— 从 `(groupID)` 变成 `({groupID, status})`，
   `MailPage` 的取数 effect 依赖数组要同步加 `status`，否则点状态项不触发重拉。
7. **状态栏时钟别用 `setInterval(…, 1000)` 直接 setState** —— 每秒一次全树渲染。
   时钟隔离成叶子组件，或干脆降到分钟级。
8. **文件夹补齐要对后端** —— 截图里有「发件箱/草稿箱/归档」，
   我们当前只支持 `inbox/junkemail/deleteditems/all`。加之前先确认
   `pkg/mailer/imapx/folders.go` 的映射覆盖到了这几个，否则 Tab 点了会空。
9. **Kumo `Tabs` 改下划线样式** —— 先确认它有没有 `variant`；没有就自建，
   不要用 `!important` 去覆写 Kumo 内部类名，那会在 Kumo 升级时静默碎掉。

## 8. 实施记录：与方案的偏离

方案是照着截图推的，落地时撞上了几处「我们的模型和它对不上」，都按**只做我们真做得到的**处理。

### 8.1 砍掉的后端工作

**不需要新增 `GET /mail/stats`。**已有的 `GET /mail/refresh/stats` 返回的
`total / success / failed / never` 正好就是「账号总数 / 登录成功 / 登录失败 / 尚未登录」，
三条聚合 SQL，左栏计数和底部状态栏共用它即可。

UI 改版本身没有改动任何后端代码；后端唯一的改动是 §8.3 那个 401 语义修复，与布局无关。

「全局未读数」拿不到：邮件不落库、是实时从上游拉的，统计全租户未读要为每个账号打一次上游
（还各扣一次 `daily_mail_fetch`）。未读数因此只在邮件列表那一栏里按已加载的算。

### 8.2 没做的按钮（功能缺口，不是 UI 工作）

参照设计里有、我们后端没有的能力，一律不摆假按钮：

| 参照设计 | 我们的处理 |
|---|---|
| 新建邮件 / 群发邮件 / 回复 / 转发 | **没做**——后端只有读取和删除，没有发信能力 |
| 邮件规则 | **没做**——无对应功能 |
| 加星筛选 | **没做**——`Message` 上没有 flagged 字段，做出来是个永远筛不出东西的标签 |
| 标为未读 | **没做**——`/messages/read` 只能标已读，没有反向操作 |
| 「开始收件」CTA | 改成**批量刷新令牌**（跳 `/mail/tokens`）——我们没有一键收件，最接近的高频入口是它 |
| 回收站 / 辅助邮箱分组 | **没做**——数据模型里没有这两个概念 |
| 详情里的删除 | **没做**——列表侧已有（勾选后的批量条），那条链路会同步更新行状态；详情里再做一份，列表不会跟着变，会看到「已删除但还在列表里」的信 |

详情操作条最后只放了**复制正文**（验证码场景的高频动作，纯本地、无同步问题）。

### 8.3 顺手修掉的两个真问题

都不是这次改版引入的，是实施过程中撞出来的：

1. **一个邮箱 token 失效会把用户本人登出。**这个 bug 直接挡住了 P2 的验证——
   点开一个 token 失效的账号就被踢回登录页。两端都修了：

   - **根因在服务端**：`upstreamFailure` 把上游的 `auth_failed` / `consent_required`
     映射成了 401。401 的含义是「本次请求的调用方没通过认证」，而这里说的是
     「调用方没问题，是他托管的那个邮箱的凭据过期了」。这同时**违反了自己的契约**：
     05 文档 §1.2 写的是 `1005 → 502`。已改回 502，具体原因仍由 `data.error_kind` 承载。
   - **前端**：`shouldClearSession(status, code)` 只对非 1005 的 401 清会话，作为第二道防线。

   两端各配一条回归用例（`TestUpstreamAuthFailureIsNotUnauthorized`、`client.test.ts`）。
   前者验证过「把服务端改回旧行为就会失败」。
2. **账号超过 50 个时，第 51 个往后在界面上不存在。**后端每页默认 50，
   前端既不传 `page` 也没有翻页控件，顶部却还写着「共 N 个账号」。P4 补上了分页。

另外修了一个改版中引入的布局 bug：账号列表用固定列宽（合计 716px），
而这一栏在 1440 视口下只有约 570px，最后一列直接溢出、画到了右栏的邮件列表上。
改成按 `@container` 切换列数——决定放不放得下的是这一栏自己的宽度，不是视口。

### 8.4 与方案不同的实现选择

- **左栏**：方案给了三个候选，最终按「状态段 + 分组树两段并列」做（不是照搬截图的嵌套）。
  我们的分组数量不定，每个分组展开四个状态子项会让面板长到没法用；并列还额外支持两个维度叠加。
- **全局搜索的状态放 URL**（`?q=`）而不是新开一个 store：结果可分享、可前进后退，
  也省掉顶栏组件和页面组件之间再拉一根全局状态的线。为此移除了筛选栏里重复的搜索框。
- **分页文案自己写**：Kumo 的 `Pagination.Info` / `PageSize` 文案是写死的英文
  （"Showing 1-50 of 50"、"Per page"）且没留接口，只借用了它的 `Controls`。
- **`AccountBatchMenu` 已删除**，批量动作并入 `MailToolbar` 并常驻（无选中时禁用），
  这样工具条高度恒定，列表不会因为勾一个复选框就整体往下跳一行。

### 8.5 验证方式

除构建/lint/测试外，用 Playwright 在真实浏览器里跑了端到端验证（独立的临时数据库，
没有碰项目的 `app.db`）：外壳不整页滚动且状态栏精确贴底、SplitPane 拖拽比例真的变化、
左栏两个维度的筛选各自生效、分页 `page=2&limit=25` 且两页内容不同、顶栏搜索联动 URL 与请求、
暗色切换、三档断点均无整页横/纵滚动、账号列表不再溢出到右栏。

新增两条回归用例：`Layout` 的两种形态（漏挂 `handle.shell` 会立刻失败）、
`shouldClearSession` 的两类 401。

## 9. 一句话总结

数据层和交互逻辑不用动，这次改的是**外壳形态**（文档流页面 → 固定应用外壳 + 状态栏）、
**分栏方式**（四栏并列 → 三栏 + 右栏纵向 split）、**左栏语义**（纯分组 → 分组 × 状态）
和**一层令牌**（Cloudflare 橙 → 紫蓝）。
其中只有第 4 项是纯视觉，前三项都会改到组件结构，建议按 §6 的顺序推进。
